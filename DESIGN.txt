# DESIGN — записка о дизайне RL-среды FinAudit

## 1. Задача и границы
Результат — *среда*: генератор синтетических книг на конец месяца со скрытыми ошибками, JSON-контракт
`reset/step` с пятью узкими действиями и оценщик. Намеренно вне рамок: обучение моделей и UI.
Всё работает офлайн на Python 3.11 + `tzdata`.

## 2. Мир и генерация
Генерация идёт в четыре прохода от одного ГПСЧ с seed `sha256(seed | хеш config | ENV_VERSION | attempt)`:
(1) **скрытая история** — компания, базовая валюта (KZT/USD/EUR), 1–3 иностранные валюты с ежедневным случайным
блужданием курса (6 знаков, курс меняется каждый день), часовой пояс из шести (включая отрицательные и с летним
временем), 6–30 контрагентов, счета к получению и к оплате, платежи, возвраты; (2) **чистые книги** по
`policy.json` (AR/REVENUE, EXPENSE/AP, BANK по курсу даты платежа, распределение AR/AP по курсу даты счёта, разница
на FX_GAIN_LOSS, дополнительные пары проводок), затем `check_invariants` (Σdr = Σcr, односторонние строки, каждая
сумма равна конвертации по policy, каждый платёж распределён полностью, всё внутри периода);
(3) **внесение ошибок** — каждый инжектор делает одно причинное изменение, записывает его (`table, id, field,
before → after`) и возвращает ошибку с суммой и наборами доказательств; (4) **рендер** — перемешанные строки,
непрозрачные ID без гласных (`INV-7F3K2Q`), разделение public/private. Затем `verify_episode` заново выводит каждое
расхождение независимым `reference_audit`, который читает только открытые файлы; любое несовпадение с `truth.json`
(в любую сторону), недостающее доказательство, размер вне диапазона или утёкшее слово отклоняют попытку, и
детерминированно берётся следующая. Verify также откатывает журнал изменений provenance и проверяет
**равенства до внесения ошибки** на восстановленных книгах (баланс, односторонние строки, проводки по каждому
документу периода, эталонный аудитор ничего не находит). Каждый набор доказательств самодостаточен: например, для
дубля нужны оба документа *и* обе проводки, для частично проведённого иностранного платежа — строка fx на дату
счёта, чтобы пересчитать сумму.

## 3. Ошибки, взаимодействия, отвлекающие случаи
Четыре независимо настраиваемых типа — дубль счёта (копия ±0–3 дня, проведена), распределение платежа (часть или
весь платёж отложен на SUSPENSE либо платёж не проведён), конвертация FX (UTC-дата, ±1–3 дня или обратный курс),
период (счёт следующего месяца проведён внутри периода) — на стороне и дебиторов, и кредиторов, ≤ 12 на эпизод.
Взаимодействия: **I1** — FX + частичное распределение одного позднего вечернего иностранного платежа в последний
день (сначала FX, обе суммы считаются после обоих изменений, порядок сохранён в provenance); **I2** — дубль,
единственный платёж по которому наполовину проведён на копию. Суммы распределения — в валюте платежа, поэтому
инжекторы выбирают разбиения, базовое значение которых точно конвертируется обратно; truth — ровно то, что
пересчитает аудитор.
Отвлекающие случаи (≥ 3 вида в каждом эпизоде, в том числе в чистых) построены так, чтобы ломать наивные правила:
разбитые платежи, платежи за несколько счетов, переплата + отрицательный возврат, еженедельно одинаковые суммы,
документы около полуночи, записанные в `+00:00`, непроведённые счета следующего месяца, строки FX gain/loss,
остаток округления в 1 единицу.

## 4. Контракт и изоляция
Фиксированная форма observation, закрытый список кодов ошибок, 100 шагов включая submit, страницы по 50 строк со
стабильными непрозрачными курсорами, калькулятор на `ast` + `Decimal`, копии записей в каждом результате (агент в
том же процессе не может изменить хранилище). В режиме eval награда всегда 0 и возвращается только `steps_used`;
env-server (он же оценщик) и агент — отдельные процессы, связанные JSON-строками через runner, в Docker работают
как пользователи `grader`/`agent`, каталоги `private/` и каталоги прогонов имеют права 700. Oracle доступен только
оценщику. Сканер утечек проверяет каждое observation, сообщение об ошибке, траекторию и открытый файл на ID
ошибок, слова truth/provenance/private/seed, названия типов ошибок, слова-подсказки и абсолютные пути.

## 5. Matcher и допуски
Реализует точные соглашения из определений проверок (docs/CHECKS.txt). Структурная проверка на исходных списках
(любой дефект → −1); строки (type, currency, ID) сравниваются точно, affected/evidence ID — как множества,
неизвестная строка типа — несопоставленный вывод (FP); допустимая пара требует тип, точное множество affected ID,
валюту, фиксированную для типа, сумму в пределах опубликованного допуска τ для типа
(`policy.json → amount_tolerance_minor`, 0 для каждого типа, нет ключа → 0) и существующие ID доказательств,
покрывающие один полный набор. Затем максимальное паросочетание в двудольном графе с опубликованным правилом выбора
(ошибки по code points `issue_id`, наименьший индекс вывода). Число TP одинаково в любом максимальном
паросочетании, поэтому неоднозначность не меняет метрики; повторные выводы становятся FP. Награда =
`clip(2·F1 − 1 − 0.002·steps, −1, 1)`, вычисляется через `Fraction` и возвращается без округления.

Жюри подключается через `judge_adapter.py` (generate_episode / make_env / score_episode, действия
`{"name", "args"}`, закрытый режим = режим eval с наградой 0 и без диагностики, 60 с реального времени на эпизод).
Это чистый слой перевода поверх `FinAuditEnv` и оценщика; `tests/test_judge_adapter.py` прогоняет контрактный
блок C01–C20.

## 6. Что проверяют тесты (287 тестов, `make check`)
Контракт и каждую ветку ошибок; адаптер жюри по контрактному блоку C01–C20; блок matcher/награды 1–20 и примеры
M01–M12 с точными числами (`tests/test_jury_matcher.py`); атаки на калькулятор; полноту пагинации и стабильность
курсоров; нормализацию matcher, границы допуска и максимальное паросочетание; 12 атак на награду с точными числами;
инварианты чистых книг и verify на 1000 seed; каждый тип ошибки отдельно (сумма, валюта, достижимые доказательства,
обе стороны, все варианты); I1/I2; отвлекающие случаи никогда не помечаются; verify ловит девять видов испорченного
truth; transform сохраняет награду oracle и не оставляет старых ID; побайтовую повторную генерацию (в том числе при
разных `PYTHONHASHSEED`); повтор траекторий; изоляцию eval (процесс от `agent` получает `Permission denied` на
`private/`); ранжирование политик; самый большой эпизод < 5 с и < 500 МБ; каждую базовую валюту × часовой пояс;
мягкие формы config; обнаружение сломанного provenance; враждебные курсоры, строки агента и зависшие pipe дают
ограниченные ошибки (`tests/test_hostile_input.py`).

## 7. Числа (`REPORT.txt`, 20 новых эпизодов, 99 ошибок, режим eval)
Средняя награда / F1: oracle **+1.000 / 1.000**, reconciler **+0.037 / 0.542**, random_explorer **−0.708 / 0.150**,
flag_all **−1.000 / 0.000**. Парные проверки 20/20, повторы 20/20, самый медленный эпизод 0.54 с с учётом запуска
процессов (лимит 60 с). Reconciler находит все 23 дубля, но пропускает все ошибки FX (26; у него нет курсов),
19 из 33 ошибок распределения (частичные распределения в иностранной валюте), 4 ошибки периода, которые по UTC
выглядят внутри периода, и даёт 21 ложную ошибку периода на документах периода, чья UTC-дата вне периода — ровно те
ловушки, ради которых среда построена. С фиксированным seed политики случайный исследователь не находит ни одной
ошибки; его средний F1 0.150 получается только на чистых компаниях, где он случайно ничего не отправляет. Эти числа
пересчитываются `make jury` + `make report`; источник истины — `REPORT.txt`.

## 8. Честные ограничения
* Данные синтетические, каталог ошибок закрыт (четыре типа, два взаимодействия); высокая награда **не**
  доказывает пригодность для реального аудита, только для этой спецификации.
* По общей формуле пустой ответ после таймаута на чистой компании получает 0.8 (1 − 0.2); формулу не меняем и
  документируем это свойство.
* Платежи всегда в валюте счёта (без кросс-валютных расчётов); суммы частичной оплаты определены через одно
  опубликованное округлённое обратное преобразование (`policy.json → payment_allocation_amount`). Допуск 0, поэтому
  агент, обращающий курс иначе (например, с округлением в другую сторону), теряет вывод — проверяется
  `test_tolerance_edges` и атакой `oracle_amount_off_tol_plus_1` (−1.0 в REPORT.txt).
* Лимит 60 с реального времени проверяется при следующем вызове `step` (`judge_adapter.py`); политику, которая
  не возвращает управление, останавливает вызывающая сторона (наш runner убивает процесс агента; жюри
  останавливает свой прогон).
* Агент с кодом генератора мог бы перебрать seed, если бы пространство seed было маленьким; seed жюри 64-битные,
  и seed никогда не появляется в открытых файлах или observations.
* Reconciler — намеренно наивная базовая политика; модели не обучались, заявлений об улучшении обучения нет.
* Внутри `PAYMENT_ALLOCATION` вариант (частично распределён / отложен на SUSPENSE / не проведён) выбирается по
  seed и не является ключом config; provenance показывает, какой вариант получил эпизод (`docs/JURY.txt`). Виды
  отвлекающих случаев включены всегда (≥ 3 на эпизод), поэтому чистые компании D01–D05 различаются seed и
  часовым поясом, а не переключателем.
