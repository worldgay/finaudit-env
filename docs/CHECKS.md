## Единый способ подключения

Используется тонкий Python-адаптер `judge_adapter.py` внутри контейнера команды. Наследование от Gymnasium не нужно; реализация среды может быть на другом языке, тогда адаптер вызывает её локально. Политики организаторов остаются одними и теми же; адаптер переводит названия типов/полей и действия конкретной команды, не меняя смысл задачи и не выбирая действия вместо политики.

### Интерфейс адаптера

```python
# Все пути и закрытые аргументы доступны только процессу жюри.
def generate_episode(seed: int, config: dict, output_dir: str) -> None:
    ...

def make_env():
    ...  # объект с reset и step ниже

# Методы объекта среды:
# reset(seed, config) -> (observation, info)
# step(action) -> (observation, reward, terminated, truncated, info)

def score_episode(episode_dir: str, findings: dict,
                  inspection_steps: int) -> dict:
    ...
```

- `generate_episode` создаёт эпизод в каталоге жюри: manifest, ledger, invoices, payments, fx, policy, а также закрытые truth и provenance из §03. Это обёртка над генератором команды, не отдельный новый генератор.
- `reset` получает `config={"mode":"closed", "episode_dir":"<каталог эпизода>", "team_config":{...}}`. В этой ветке он загружает именно переданный эпизод, не генерирует другой и не меняет ID. Повторный reset начинает его заново. Для открытого режима `mode="train"`; без `episode_dir` используется генератор команды с переданными seed и team_config.
- `step` принимает JSON-объект `{"name": "<действие>", "args": {...}}`. Обязательные имена: `list_records`, `get_record`, `get_document`, `calculator`, `submit`. Аргументы соответствуют §04; у submit это `{"findings": <объект findings.json из §05>}`. Адаптер может переводить эту оболочку во внутренний формат команды.
- `score_episode` для валидного submit возвращает `{"tp": int, "fp": int, "fn": int, "precision": number, "recall": number, "f1": number, "return": number}`. Это закрытый вызов оценщика, не действие политики. Невалидный submit даёт `return=-1`, остальные поля равны null, ошибка записывается в журнале оценщика; эти null-метрики не используются для ранжирования.
- Канонические имена таблиц адаптера: `ledger`, `invoices`, `payments`, `fx`; поля записей соответствуют §03. Внутренние имена команда переводит в адаптере.
- Первое observation: `{"task": str, "manifest": object, "policy": object, "remaining_steps": 100}`. Следующие observation: `{"result": value_or_null, "error": null_or_object, "remaining_steps": int}`. Ошибка содержит публичный код и краткое сообщение без путей, seed и закрытых данных.
- Результат list_records: `{"records": [object], "next_cursor": null_or_string}`; get_record и get_document возвращают объект запрошенной записи/документа; calculator возвращает десятичную строку; submit возвращает только `{"accepted": true}` либо ограниченную ошибку структуры, без оценки правильности. Код ошибки не раскрывает факт совпадения с truth. В info нет закрытых данных.
- Для `list_records` используются `table`, `cursor`, `limit`; первый cursor равен null. Для остальных действий: `table, id`; `doc_id`; `expression`; `findings`. Команда документирует допустимые имена таблиц и представление результатов. Одна и та же общая политика использует эти имена через адаптер, а не через отдельную переписанную стратегию.
- Код адаптера, схема результатов и соответствие четырёх типов ошибок описываются в README. В контейнере жюри вызывает одинаковые точки входа; команда указывает рабочую директорию и команду запуска в README. Новый обязательный базовый образ или система сборки не вводятся.

### Граница доступа

`generate_episode`, пути, seed, config, truth, provenance и `score_episode` остаются у жюри. Политика работает в отдельном ограниченном процессе и получает только разрешённые наблюдения и результат вызова step. Она не импортирует оценщик и не получает доступ к каталогу эпизода. Простое сокрытие полей в Python-объекте не считается изоляцией. В закрытом режиме reward в ответе политике равен 0, включая завершение; истинная награда вычисляется и хранится отдельно. В train терминальная награда доступна политике.

Общие политики организаторов: случайное исследование с фиксированным seed, простая сверка, массовая пометка, oracle. Oracle строит правильные findings из закрытого truth только на стороне жюри и отправляет их обычным submit. Наличие у oracle эталона не расширяет доступ остальных политик.

### Как подаются парные проверки

Используется загрузка файлов, а не переключатель преобразования у команды:

1. Жюри вызывает `generate_episode` один раз и сохраняет исходный комплект.
2. Жюри создаёт отдельную копию, переставляет записи и/или согласованно меняет ID во всех данных и ссылках. Truth и provenance меняются в закрытой части этой копии. Содержимое исходного эпизода не перезаписывается.
3. Оба варианта подаются в `reset` через один и тот же `episode_dir`. Seed/config генерации исходного эпизода фиксируются; преобразование также имеет зафиксированные параметры. Отдельного `transform=true` или специфичного алгоритма перестановки от команды не требуется.
4. На исходном варианте повторяются те же действия. На преобразованном oracle отправляет правильные findings с новыми ID; сравнение выполняется после обратного отображения ID и с одинаковым числом исследовательских шагов.

Имена новых функций, envelope действий и `episode_dir` отсутствуют в исходном кейсе. Это единый транспорт для уже требуемых проверок, одинаковый для всех команд.

### Общие пограничные решения

- Submit считается одним из 100 действий, но не входит в `inspection_steps`. Все предыдущие вызовы step, в том числе ошибочные, входят в inspection_steps. Submit на действии 100 принимается; 100 исследовательских действий без submit завершают эпизод как truncated.
- Лимит времени: 60 секунд на эпизод, как в лимите §07: от начала reset до завершения, включая работу политики, без сборки контейнера и подготовки фикстуры. При превышении жюри останавливает прогон и учитывает пустые findings. Характеристики машины объявляются отдельно и одинаковы для всех.
- JSON сравнивается по значениям, не по пробелам/порядку ключей. Списки сохраняют порядок, кроме явно объявленных множеств. Повторный запуск должен точно воспроизводить записи, переходы и награды в этом смысле.

## Общие фикстуры

Используются типы ошибок, схемы и действия исходного кейса. Нижеописанные эпизоды загружаются через episode_dir из протокола подключения.

- **C:** чистый эпизод с существующими записью R1 и документом D1; список таблиц и существующие ID оценщик знает из самой фикстуры, не передаёт их политике скрытым каналом.
- **E:** эпизод с одной заявленной ошибкой и полным доступным набором доказательств; нужен для проверки разделения обучающего и проверочного режимов.
- **L:** валидный эпизод с таблицей не менее 101 записи, чтобы проверить три страницы. Если команда использует размер из предложенного диапазона 200-2000, он уже подходит. Создание большой таблицы для теста - выбор фикстуры, не новое минимальное требование к каждому эпизоду.
- **U:** идентификатор, которого нет в открытых данных фикстуры. Он выбирается после чтения данных оценщиком, а не предполагается несуществующим по внешнему виду.

Во всех проверках сначала выполняется reset. Окружение, версия, seed и config записываются в закрытый журнал оценщика. Сравнение награды выполняется на стороне оценщика, не через ответ агенту.

Кейс требует минимум два сценария взаимодействия и приводит пример, а не фиксирует их состав. Поэтому здесь используются именно два сценария, которые реализовала и документировала команда. Жюри не подменяет их неанонсированным обязательным сочетанием.

### Условие зачёта каждого эпизода

Эпизод даёт один pass только при выполнении всех условий, уже предусмотренных кейсом:

1. До внесения ошибки книги согласованы. История генерации и изменений в provenance вместе с исходными документами позволяет независимо проверить это состояние. Конкретный формат provenance команда документирует; проверка не требует неизвестного поля или недоступного факта.
2. Инъекция создаёт именно заявленное расхождение. Проверка выполняется по исходному и изменённому состоянию независимо от matcher команды. Для платежа это проверка фактического распределения, для FX - вычисление по policy, для периода - дата/граница, для дубля - повторное отражение одного обязательства. Нельзя считать любое ненулевое сальдо достаточным доказательством любой ошибки.
3. Тип, affected_ids, ожидаемая сумма и валюта в truth соответствуют реальному изменению. Чистый эпизод не содержит эталонных ошибок.
4. Хотя бы один полный допустимый набор доказательств доступен через объявленные инструменты. По нему можно проверить вывод, не читая truth и не угадывая недоступные факты.
5. Форматы раздела 03 сохранены: время со смещением, деньги в минимальных единицах, десятичные FX-курсы, явные null вместо угаданных связей. Дополнительные документированные поля допустимы, если не раскрывают эталон.
6. Нет противоречивых или неразрешимых данных. Непонятность из-за отсутствующего доказательства не засчитывается как сложность.

**Необходимая реализация жюри:** независимые сверки должны учитывать документированные проводки и policy конкретной среды. Универсальную формулу для всех бухгалтерских схем исходный кейс не задаёт. Нельзя объявлять корректность доказанной только потому, что собственный matcher команды принял собственный oracle.

## Общая фикстура

Эталон содержит одну ошибку A. Используйте один уже поддерживаемый средой тип T, одну существующую каноническую запись R1, сумму 10000 минимальных единиц KZT и один допустимый набор доказательств {D1, D2}. Оба доказательства доступны через инструменты. Допуск в ЭТОЙ тестовой фикстуре равен нулю. Это не устанавливает нулевой допуск для всех эпизодов.

Правильный вывод F совпадает с A по T, каноническим affected_ids, сумме и валюте, содержит D1 и D2 и допустимое короткое explanation. В тестах, кроме явно указанного изменения, все поля валидны. Неправильный тип выбирается из другого уже поддерживаемого типа, не вводит новую задачу. Несуществующие ID тестовой фикстуры действительно отсутствуют среди её записей.

В unit-тестах формулы inspection_steps задаётся напрямую, по умолчанию 10. В эпизодном прогоне считаются все действия до submit, включая ошибочные; submit учитывается в лимите 100 действий, но не в inspection_steps.

## Блок 4. Двадцать парных проверок, 15 баллов

### Матрица преобразований

Для каждой D01-D20 берётся исходный эпизод и один его преобразованный вариант. Это отдельный блок оценки, а не ещё 20 оценок качества данных.

| Пары | Преобразование |
|---|---|
| P01-P05 на D01-D05 | Перестановка порядка записей без изменения значений. |
| P06-P10 на D06-D10 | Взаимно однозначная замена ID, без изменения делового смысла и порядка записей. |
| P11-P20 на D11-D20 | Перестановка порядка и взаимно однозначная замена ID вместе. |

Кейс требует 20 парных проверок; распределение 5/5/10 задано этими определениями.

### Правила безопасного преобразования

- Переставляются записи таблиц и потоки документов, но не семантически упорядоченные части документа. Порядок line_items или иной значимый порядок нельзя считать безвредным без проверки схемы.
- Заменяются идентификаторы и все ссылки на них согласованно: row_id, doc_id, invoice_id, payment_id, entity_id, affected_ids и evidence_ids. Связи, null и суммы сохраняются. Разные пространства ID учитываются отдельно, чтобы одинаковые строки в разных таблицах не стали ложной связью.
- Скрытые truth и provenance корректируются только в закрытом процессе оценщика, агент их не получает. Дополнительные документированные поля со ссылками тоже требуют согласованной замены.
- Ключ FX на основе date:source_currency:target_currency не является случайным surrogate ID: нельзя менять дату или валютную пару под видом смены ID. При перестановке он по-прежнему ссылается на ту же запись. Документированный различитель повторяющихся ключей сохраняет однозначность.
- Для подачи вариантов используется episode_dir из раздела подключения: преобразования делает жюри в копии эпизода.

### Pass/fail пары

1. На исходном эпизоде повтор с теми же seed, config, версией и действиями точно воспроизводит записи, переходы и награды. Reset не сохраняет состояние прошлого эпизода.
2. На преобразованном варианте oracle подаёт те же правильные выводы с переназначенными ID. После обратного отображения ID совпадают типы, затронутые записи, суммы, валюты и доказательства.
3. TP, FP, FN, P, R, F1 и терминальная награда совпадают. Для сравнения награды oracle использует одинаковое inspection_steps на обеих сторонах. Изменившееся число шагов нельзя скрывать за требованием инвариантности F1.
4. Не появилось нового канала утечки или недоступного доказательства. Неизменность reward при сломанном наборе доказательств не является проходом.

**Способ сравнения:** JSON сравнивается по значениям, порядок ключей объекта не важен. Порядок списков значим, кроме тех, которые документированы как множества. Числовые значения денег сравниваются точно как целые; строки FX не преобразуются в двоичный float при пересчёте. Упаковка контейнера, JSON-пробелы и побайтовая идентичность файлов не оцениваются. Это не ослабляет требование точного повторения наблюдаемых записей, переходов и наград.

**Не считается требованием:** после смены ID произвольная политика должна выбрать буквально те же действия. Проверяется правильность oracle с обратным отображением ID. Политика может использовать порядок или ID для выбора исследования, поэтому её собственная траектория не обязана быть инвариантной.

## Точные соглашения matcher

## Нормализация

1. **ID:** сравнивать строки точно, с учётом регистра и пробелов. Не преобразовывать число в строку, не удалять префиксы, не искать похожие ID. Смена ID в парных проверках выполняется отдельным явным взаимно однозначным отображением оценщика.
2. **affected_ids:** трактовать как множество точных ID. Порядок и повторы одного ID внутри списка не меняют множество. Для TP множество должно точно совпасть с одним каноническим набором затронутых ID эталонной ошибки. Канонические правила по каждому типу ошибок публикует команда в коде matcher, а не выбирает после прогона. Это не позволяет угадывать дополнительную затронутую запись «на всякий случай».
3. **evidence_ids:** трактовать как множество после проверки исходного лимита 10 элементов. Порядок и повторы не помогают. Для TP требуется полное включение хотя бы одного допустимого набора доказательств. Дополнительные существующие доступные доказательства допустимы и не обязаны входить в минимальный набор. Если указан несуществующий или недоступный evidence_id, вывод не сопоставляется и даёт FP, а не раскрывает закрытую запись.
4. **type:** точное совпадение с одним из документированных значений типа команды. Не вводится новый универсальный список имён типов или неявных синонимов.
5. **currency:** точное совпадение с кодом валюты в manifest/policy и truth команды. Автоматическая конвертация, смена регистра и обрезка пробелов не выполняются. Требование именно ISO-кода или новый список валют этим проектом не вводится.
6. **claimed_amount_minor:** JSON-целое число, не bool, строка или дробное число. Сравнивать в целых минимальных единицах. Правильность explanation не компенсирует неправильные поля.
7. **Лимиты:** сначала проверить структуру и исходные размеры списков/текста. Только потом нормализовать множества. 31 вывод, 11 ID доказательств в одном выводе или explanation длиннее 1000 символов - неверная структура всего submit и награда -1, как в кейсе. Длина считается в Unicode code points после декодирования JSON, не байты UTF-8 и не визуальные графемы. Число с логическим типом не принимается за денежную сумму.
8. **Неудачное сопоставление против невалидной структуры:** неверный тип значения/отсутствующее обязательное поле/превышение лимита - структурная ошибка submit. Структурно правильный вывод с неправильным type, affected_ids, валютой, суммой или доказательством - FP, не авария всего эпизода. Неизвестный строковый тип ошибки считается несопоставимым, а не новым обязательным сценарием.

## Допуск суммы

По умолчанию сравнение целых минимальных единиц точное: τ=0. Если конкретный тип допускает разницу из-за документированного округления, команда заранее публикует фиксированный неотрицательный целочисленный τ для этого типа/правила в policy или документации matcher. Нельзя выбирать τ по ответу агента, скрытому seed или после просмотра результатов. Новый обязательный ключ файла не вводится: используется документированный способ команды.

Условие суммы: abs(claimed_amount_minor − expected_amount_minor) ≤ τ. В каждой тестовой фикстуре τ указан явно. Кейс требует явно указанного допуска, но не задаёт его численное значение; этими определениями по умолчанию установлено τ=0.

## Неоднозначные совпадения и повторы

Построить двудольный граф: слева каждый поданный вывод, включая повторы как отдельные вершины; справа каждая отдельная ошибка truth. Ребро существует только при выполнении всех условий TP. Выбрать matching максимальной мощности. TP - число выбранных рёбер, FP - число выводов минус TP, FN - число ошибок минус TP.

При нескольких matching одинаковой мощности выбрать детерминированно: эталонные issue_id сортируются лексикографически по Unicode code points; затем выбирается лексикографически наименьшая отсортированная последовательность пар (issue_id, индекс вывода во входном findings, начиная с 0). Для этого не требуется новый формат ID. Порядок findings может менять только то, какой идентичный вывод оказался сопоставлен, но не TP/FP/FN и награду. Утечка issue_id политике не допускается.

Максимальное паросочетание, в отличие от жадного выбора первого совпадения, не теряет TP из-за порядка списка. Повторный вывод не сливается с первым: он остаётся отдельным FP, если ошибка уже сопоставлена. Объяснение не участвует в выборе рёбер.

## Числовое сравнение результатов

TP/FP/FN, денежные значения и шаги сравниваются точно как целые. Формулы метрик и reward математически фиксированы кейсом. Для проверки вещественного результата реализации допускается абсолютная погрешность не более 10^-9, без относительной погрешности. Она относится только к представлению результата вычисления, не расширяет денежный допуск τ и не меняет clipping [-1, 1].

## Изменения

Если определения уточнятся, обновлённый текст публикуется на этой же странице одинаково для всех команд, с датой изменения и списком правок. Новые виды проверок задним числом не вводятся. Скрытыми остаются только seed и конкретные значения эпизодов.
